# Arabic PDF → RAG | المشكلة العربية

## المشكلة
الـPDF العربي قد يبدو صحيحًا بصريًا لكنه لا يحتوي بالضرورة طبقة Unicode سليمة. أكثر ما واجهناه:

- ترتيب RTL مختلط مع أرقام/حواشٍ/هوامش.
- تشكيل وligatures تؤدي إلى تفتيت الكلمات.
- خطوط قرآنية خاصة أو glyph mapping غير قياسي.
- نصوص تظهر بصريًا كآية صحيحة لكن استخراجها النصي مشوه.
- اختلاف page number في PDF عن printed page.
- صعوبة فصل العناوين والأسئلة عندما تبدأ عدة وحدات في الصفحة نفسها.

## لماذا هذا مهم للـRAG؟
إذا تم embedding لنص مشوه، فقد يبدو الاسترجاع ناجحًا تقنيًا لكنه يسترجع مادة ناقصة أو اقتباسًا غير موثوق. لذلك صحة الـchunk والصفحة والـlineage جزء من جودة RAG، وليست preprocessing ثانويًا.

## السياسة الحالية
1. لا نُدخل PDF الخام مباشرة إلى pipeline الإنتاجي.
2. نعالج الكتاب خارج n8n ثم ننتج JSONL.
3. لا نعيد بناء الآيات المتضررة بالتخمين.
4. نحفظ `pdf_pages` و`printed_pages` و`chunk_id` و`document_id`.
5. نستخدم `has_special_quran_glyphs` و`review_required` عند الحاجة.
6. نحافظ على نص المؤلف قدر الإمكان ولا نلخصه أثناء تجهيز قاعدة المعرفة.

## حالة بصائر
التجزئة والبنية اجتازتا QA، لكن وجود 781 صفحة عليها special-glyph flag يعني أن «نجاح JSONL» لا يساوي «حل مشكلة استخراج كل glyph عربي/قرآني». نحتاج مراجعة مرشدين لمسار extraction أقوى أو استراتيجية تمثيل مزدوج.

## سؤال معماري للمرشد
هل الأفضل حفظ حقلين لكل chunk؟
- `retrieval_text`: نسخة normalized للبحث والـembedding.
- `source_text`: نسخة مصدر-محافظة للاقتباس والعرض.

مع hash/lineage واضح يثبت أن كلاهما يعود إلى نفس الصفحة والوحدة.
